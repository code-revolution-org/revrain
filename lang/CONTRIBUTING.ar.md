# دليل المساهمة

شكراً لاهتمامك بالمساهمة في revrain! نرحب بالإبلاغ عن الأخطاء وتحسين الوثائق والمساهمات البرمجية.

revrain قالب Hugo صُمم لعشاق التقنية والمطورين: تصميم داكن مع رسوم متحركة للمطر الرقمي، وجماليات الزجاج المثلّج (glassmorphism)، ودعم 11 لغة، والتوافق مع معيار الوصول WCAG 2.2 AA. كل مساهمة منك ثمينة.

## الفروع

يحتوي هذا المستودع على فرعين رئيسيين:

- `main`: الإصدار الرسمي / المستقر. يدمجه وينشره المشرفون من `dev` فقط. **لا نقبل Pull Request مباشرة إليه.**
- `dev`: فرع التطوير. جميع الميزات والإصلاحات وتغييرات الوثائق تُرسل إلى `dev`.

> مهم: عند فتح Pull Request، اختر `dev` كفرع الهدف، وليس `main`.

## كيف يمكنك المساهمة

- الإبلاغ عن الأخطاء
- اقتراح ميزات جديدة
- تحسين الوثائق (بما في ذلك ترجمات README متعددة اللغات داخل `lang/`)
- إرسال إصلاحات برمجية أو ميزات جديدة
- المساعدة في الاختبار وإبداء الملاحظات (خاصة عبر المتصفحات المختلفة وقارئات الشاشة واللغات المكتوبة من اليمين إلى اليسار RTL)

## بيئة التطوير

- Hugo >= 0.163.0 (أي إصدار؛ يتم تجميع SCSS بواسطة Dart Sass الخارجي)
- Dart Sass (يجب تثبيته وإضافته إلى PATH؛ يستدعيه Hugo تلقائيًا)

### المعاينة المحلية

```bash
cd exampleSite
hugo server
```

ملف `exampleSite/hugo.toml` يشير بالفعل إلى جذر القالب عبر `themesDir = "../../"`، فلا حاجة لإعدادات إضافية. لبناء نسخة الإنتاج:

```bash
cd exampleSite
hugo --minify --gc
```

## الإبلاغ عن المشكلات

قبل فتح Issue، ابحث أولاً عما إذا كانت هناك مشكلة مشابهة موجودة بالفعل.

يرجى تقديم أكبر قدر ممكن من المعلومات:

- بيئتك (نظام التشغيل، إصدار Hugo، المتصفح، إلخ)
- خطوات إعادة الإنتاج
- النتيجة المتوقعة
- النتيجة الفعلية
- سجلات الأخطاء أو لقطات الشاشة (إن وجدت)

بالنسبة للمشكلات المتعلقة بإمكانية الوصول (التنقل بلوحة المفاتيح، قارئات الشاشة، التباين، RTL، إلخ)، يرجى ذكر التقنية المساعدة المستخدمة وإصدارها.

## إرسال الكود

1. اعمل Fork لهذا المستودع.

2. استنسخ المستودع الذي قمت بعمل Fork له:

   ```bash
   git clone https://github.com/اسم-المستخدم-الخاص-بك/revrain.git
   cd revrain
   ```

3. انتقل إلى فرع `dev`:

   ```bash
   git checkout dev
   git pull origin dev
   ```

4. أنشئ فرعك من `dev`:

   ```bash
   git checkout -b fix/وصف-المشكلة
   ```

   أسماء الفروع المقترحة:

   - `feat/ميزة-جديدة`
   - `fix/إصلاح-مشكلة`
   - `docs/تحديث-وثائق`

5. عدّل الكود ونفّذ الالتزام (commit):

   ```bash
   git add .
   git commit -m "fix: إصلاح مشكلة محددة"
   ```

6. ادفع إلى مستودعك:

   ```bash
   git push origin fix/وصف-المشكلة
   ```

7. افتح Pull Request على GitHub.

   **يجب أن يكون الفرع الهدف للـ PR هو `dev`، وليس `main`.**

## متطلبات Pull Request

- الفرع الهدف: `dev`
- يُفضَّل أن يقوم الـ PR الواحد بعمل واحد فقط
- اشرح ما الذي تغيّر ولماذا وكيف تم اختباره
- للتغييرات الكبيرة، يُنصح بفتح Issue للمناقشة أولاً
- لا تُدرج تنسيقات غير ذات صلة أو تغييرات واسعة النطاق
- لا ترفع كلمات مرور أو مفاتيح أو معلومات شخصية
- عند تغيير سلوك القالب، حدّث `README.md` وفقاً لذلك (وعند الحاجة الوثائق متعددة اللغات داخل `lang/`)
- بعد تعديل الأنماط أو السكربتات، تحقق محلياً باستخدام `hugo server` وتأكد من الأداء الصحيح على الشاشات الضيقة (الجوال)
- عند إضافة أو تعديل تفاعلات الواجهة، حافظ على اتفاقيات إمكانية الوصول الحالية: التشغيل بلوحة المفاتيح، تركيز مرئي، وسوم `aria-*`، ودعم `prefers-reduced-motion`

## اقتراحات رسائل الالتزام

موصى بها لكنها ليست إلزامية (حافظ على أسلوب الالتزام الحالي):

- `feat: ميزة جديدة`
- `fix: إصلاح خطأ`
- `docs: تحديث وثائق`
- `test: اختبارات`
- `refactor: إعادة هيكلة`
- `chore: أعمال متنوعة`

## عملية إصدار المشرفين

التطوير المعتاد يتم في `dev`.
عندما يستقر `dev` بعد الاختبارات، يدمجه المشرفون في `main` وينشرونه كإصدار رسمي.
